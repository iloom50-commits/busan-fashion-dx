# 개인정보 최소화 + 로컬 임시저장 설계

작성일: 2026-08-13
대상: 2026 부산 패션(봉제) 소공인 DX 역량진단 도구

## 배경

### 해결하려는 문제

1. **개인정보 노출** — Firestore 보안규칙이 열려 있어, 인증 없이 저장된 모든 기업의
   기업명·대표자·연락처·이메일을 읽을 수 있다. 2026-08-13 실측으로 확인했다.
   브라우저에서 Firestore에 직접 질의해 전체 기록을 받아냈으며, 진단자 접속 코드를
   입력하지 않고도 가능했다.

2. **작성 중 데이터 유실** — 전문가 진단의 진행 상태가 브라우저 메모리에만 있어,
   새로고침·탭 종료·배터리 방전 시 입력이 전부 사라진다. 현장 진단은 20~30분 걸린다.

3. **기존 기록 훼손 가능** — 규칙이 열려 있어 저장된 진단을 누구나 수정·삭제할 수 있다.

### 전제 조건

- 진단 대상은 부산테크노파크가 지정한 **10개사**
- 과업기간은 2026-09-30까지이며, 이후 이 도구를 재사용할 계획은 없다
- 대표자·연락처 명부는 부산테크노파크가 이미 보유한다 (과업지시서 66행)
- 2026-08-13 기준 저장된 자가진단은 1건(그린섬유), 전문가 진단은 0건

## 채택한 접근

**저장하지 않은 정보는 유출되지 않는다.**

백엔드를 세워 읽기를 차단하는 대신, 개인정보를 애초에 서버에 보내지 않는다.
서버·세션·서비스 계정 키·보안규칙 같은 관리 대상이 생기지 않으므로
같은 문제를 더 적은 코드로 없앤다.

### 검토했으나 채택하지 않은 안

| 안 | 내용 | 미채택 사유 |
|---|---|---|
| Vercel 서버리스 백엔드 | 인증·조회를 서버로 이전 | 10개사·7주 규모 대비 과함. 서비스 계정 키 관리가 새로 생김 |
| Railway 통합 백엔드 | Express + Postgres로 전면 이전 | 구조는 가장 깨끗하나 2일 소요. 재사용 계획이 없어 회수되지 않음 |
| Firebase Auth 도입 | 계정 기반 인증 | 계정 관리 부담. 진단자 로그인 방식이 코드에서 이메일로 바뀜 |
| 읽기 전면 차단 | 규칙으로 read 차단 | 자가진단 연계·관리자 대시보드가 모두 동작 불능 |

## 설계

### 1. Firestore 저장에서 개인정보 제외

입력 폼과 화면은 그대로 두고, **Firestore로 보내는 필드에서만** 제외한다.
대표자·연락처는 브라우저 메모리에 남아 PDF 리포트에 정상 출력된다.
리포트는 로컬에서 생성되므로 서버를 거치지 않는다.

| | Firestore에 저장 | 저장하지 않음 |
|---|---|---|
| 자가진단 | company, bizNum, emp, bizType, track, gradeLv, gradeTxt, totalScore, scores | **ceo, phone, email** |
| 전문가진단 | company, bizNum, emp, track, selfRef, selfScores, gradeLv, gradeTxt, totalScore, scores, causes, solutions, roadmap, opinion | **ceo, phone, email** |

자가진단 입력 화면에 안내 문구를 추가한다:
"연락처와 대표자명은 결과보고서 출력에만 사용되며 서버에 저장되지 않습니다."

**영향**: 전문가 툴이 자가진단을 불러올 때 대표자·연락처가 채워지지 않는다.
진단자가 현장에서 입력하거나 부산테크노파크 명부에서 확인한다.
관리자 대시보드의 대표자 열은 제거한다.

### 2. 전문가 진단 자동 임시저장 (브라우저 로컬)

`localStorage`에 진행 상태를 저장한다. 네트워크와 무관하게 동작하므로
현장 통신 상태가 나빠도 영향을 받지 않는다.

- **저장 시점**: `render()` 호출 시마다. 상태가 바뀌는 모든 경로를 자연스럽게 덮는다
- **저장 키**: `dx-expert-draft`
- **저장 대상**: `state` 전체 (사진 제외 — 사진은 현재도 `state`에 담기지 않는다)
- **복원**: 로그인 직후 저장된 임시본이 있으면 안내를 띄운다
  → "작성 중이던 진단이 있습니다: ○○봉제 (6/9단계) [이어서 작성] [새로 시작]"
- **삭제**: 진단 완료 저장에 성공하면 임시본을 지운다. `restart()` 시에도 지운다

**제약**: 현장 사진은 복원되지 않는다. 이어서 작성할 때 다시 첨부한다.
사진을 복원하려면 Firebase Storage가 필요하며 이번 범위에서 제외한다.

**제약**: 임시본은 그 기기·그 브라우저에만 있다. 다른 기기에서는 이어서 할 수 없다.
진단자 1인이 한 기기로 10개사를 도는 전제에서 문제되지 않는다.

### 3. Firestore 보안규칙 게시

- `allow update, delete: if false` — 기존 기록 훼손 차단
- `allow create: if isValidDiagnosis()` — 필드 검증, serverTimestamp 강제
- `allow read: if true` — **의도적으로 열어 둔다.** 개인정보가 저장되지 않으므로
  노출되는 것은 기업명·사업자번호·진단점수이며, 이를 감수하는 대신
  자가진단 연계와 관리자 대시보드를 백엔드 없이 유지한다

기존 `firestore.rules`는 Firebase Auth 도입을 전제로 작성되어 있으므로
이 결정에 맞게 주석과 read 규칙을 갱신한다.

### 4. 전문가 진단 결과 JSON 내보내기

결과 화면에 "결과 JSON 저장" 버튼을 추가한다.
담당자가 파일 사본을 보유하며, Firestore에 없는 대표자·연락처도 포함된다.
자가진단의 `exportSelfResult()`와 같은 방식이다.

## 범위 밖

- **진단자 홈 화면 / 내 진단 목록** — 10개사를 1인이 진행하는 전제에서 가치가 낮다.
  전체 현황은 관리자 대시보드에서 확인한다
- **여러 기기 간 이어서 작성** — 서버 저장이 필요하므로 제외
- **현장 사진의 저장·리포트 반영** — Firebase Storage가 필요. 별도 과제로 남긴다
- **전문가 진단 리포트 개편** — 자가진단과 달리 구버전 방식(`#print-area` + `window.print()`)이
  남아 있다. 이번 작업과 독립적인 별도 과제

## 완료 기준

1. 자가진단을 제출한 뒤 Firestore 문서에 `ceo`·`phone`·`email` 필드가 **없다**
2. 같은 진단의 PDF 결과보고서에는 대표자명·연락처가 **정상 출력된다**
3. 전문가 진단을 작성하다 새로고침하면 복원 안내가 뜨고, 이어서 작성하면
   입력했던 점수·원인·솔루션이 그대로 복원된다
4. 진단을 완료 저장한 뒤에는 복원 안내가 뜨지 않는다
5. 규칙 게시 후, 브라우저에서 기존 문서 수정·삭제를 시도하면 **거부된다**
6. 자가진단 제출은 규칙 게시 후에도 정상 동작한다
7. 진단자의 자가진단 불러오기와 관리자 대시보드가 규칙 게시 후에도 동작한다

## 작업 순서

되돌릴 수 있는 단위로 나눈다. 각 단위마다 검증한다.

1. Firestore 저장 필드에서 개인정보 제외 (index.html, expert.html, admin.html)
2. 전문가 진단 자동 임시저장·복원 (expert.html)
3. 전문가 진단 결과 JSON 내보내기 (expert.html)
4. `firestore.rules` 갱신 → **사장님이 Firebase 콘솔에서 게시**
5. 게시 후 전체 흐름 재검증

규칙 게시(4)를 마지막에 두는 이유는, 검증 중 데이터 정리가 필요할 수 있는데
`allow delete: if false`가 걸리면 콘솔에서만 지울 수 있게 되기 때문이다.
